# Web App

浏览器里跑完整条流水线：贴脚本 → 选模型 → 生成 → 对话式改片 → 导出下载。

```
python -m uvicorn web.server:app --port 8787
# 打开 http://127.0.0.1:8787
```

需要 `pip install -e ".[web]"`。

依赖里必须是 **`uvicorn[standard]` 而不是裸 `uvicorn`**：前者会带上 `websockets`，
没有它 uvicorn 完全处理不了 WebSocket 升级，每个 `/ws/...` 请求都会返回 404，
进度条就只能退化成前端轮询（功能还在，但进度不实时）。

等价命令：`pip install fastapi "uvicorn[standard]" python-multipart`。

## 前端技术栈

`web/frontend/` 是一个独立的前端工程：

| | |
|---|---|
| 构建 | Vite 6 + React 18 + TypeScript（strict） |
| 样式 | Tailwind CSS 3 + CSS 变量主题（浅/深） |
| 组件 | shadcn/ui 风格组件（Radix 原语 + CVA），源码在 `src/components/ui/` |
| 图标 | lucide-react |
| 多语言 | react-i18next，中/英两套文案；**默认英文**（不嗅探浏览器语言），切换后写入 localStorage |
| Toast | sonner |

构建产物输出到 `web/static/dist/`，由 FastAPI 直接托管（`/` 与 `/assets`），
**已提交进仓库**，所以 clone 下来不装 node 也能跑。旧的单文件页面仍在
`/legacy` 作为回退。

```bash
cd web/frontend
npm install
npm run dev        # http://127.0.0.1:5273，/api 与 /ws 代理到 8787
npm run build      # -> web/static/dist
npm run typecheck
```

改文案只动 `src/i18n/locales/{zh,en}.ts`；加厂商只动
`avb/provider_specs.py`（服务端）+ 对应语言文件里的 `vendor.*` 键。
厂商的模型清单同样来自 `provider_specs.py`（`models` / `model_env`），
设置页自动渲染成下拉框，并保留"自定义模型 id"输入框——厂商改模型名
（Seedance / Kling / MiniMax 都干过）时不用等发版。

## 界面

顶部三个标签页：**创作** / **历史** / **设置**。设置只管"去哪家拿素材"，
创作是一条五步流水线，历史负责找回过去的成片与脚本。

### 创作页的五步

| 步骤 | 干什么 | 花不花钱 |
|---|---|---|
| 1 脚本 | 填产品简报（产品名/特性/卖点/分类/语言），选风格/画幅/模型 | 不花钱 |
| 2 确认文案 | **看并改**模型产出的场景口播、字幕与画面提示词 | 不花钱 |
| 3 生成视频 | 确认后才真正调用配音 + 视频模型；可选分辨率与字幕 | **从这里开始计费** |
| 4 微调 | 自然语言改片，只重渲受影响的场景 | 按重渲场景数计费 |
| 5 导出 | 下载 MP4，自行上传到任意平台 | — |

为什么要在第 2 步停下来：模型的分镜初稿经常读起来不对，而重新生成八段素材
是真金白银。**先确认再烧钱**是这个流程存在的唯一理由。

第 2 步每一场都可以：改口播/字幕文案、改画面提示词、上下移动、删除，
也能「重新分镜」让模型再跑一次。字幕没有独立输入框——它靠这一行的词级
时间轴驱动，两者是同一份文本，改一个另一个跟着变。

第 4 步的「应用改动并重渲染」开关默认打开：关掉只返回分析结果不动画面。
打开时服务端 diff 出受影响的场景，只重渲这些，其余走缓存。

### 设置页

左侧是 Provider 配置与状态，右侧是一页说明 + 运行日志。
没配视频 Provider 时标签上会挂一个红点，点「生成场景文案」也会被拦下并跳回设置页。

| 区块 | 说明 |
|---|---|
| 视频生成模型 | Seedance / Kling / 即梦 / Veo / Wan / Hailuo / CogVideoX / 自动。选中哪家就显示哪家需要的 key（即梦是 AccessKey+SecretKey 双 key，其余单 key） |
| 模型版本 | 有得选的 provider（如 Seedance 的 pro / mini）在这里挑 |
| 配音 | Edge TTS（免费）/ ElevenLabs / Formant（离线） |
| LLM | DeepSeek 或任意 OpenAI 兼容端点，可改 Base URL 与 model |

- 已配置的 key 只显示掩码，输入框**留空 = 不修改**，不会清空已有值。
- Key 写入 `.env`（不进 git），模型选择写入 `avb.toml`。
- 保存后立即生效：服务端同步更新 `os.environ` 并重建 LLM client，不用重启。

#### 第 1 步的控件

| 控件 | 说明 |
|---|---|
| 脚本语言 | 决定脚本和分镜用什么语言写。默认跟界面语言走 |
| 产品名 | 例：Lumo 助眠灯。也提供几个示例，点一下自动填充整份简报 |
| **产品特性** | **写清楚它「是什么」，不只是「有什么用」**。例：`53度酱香型白酒 / 赤水河核心产区 / 五年陈酿 / 红标陶瓷瓶` |
| 卖点 | 每行一个。例：`入睡速度快 2 倍` |
| 分类 | 15 个常见电商品类（3C 数码 / 美妆护肤 / 食品饮料…），可直接输入自定义 |
| 目标人群 / 调性 | 可多选，也能自己写新标签 |
| 视频时长 | 目标总时长 5–60 秒，±5 步进。各场景等比拉伸，配音与字幕同步 |
| 参考图 | 产品三视图，最多 9 张。AI 视频所有镜头保持产品外观一致 |
| 用 LLM 写脚本 | 关掉 = 用确定性模板（离线可用）；打开 = 文案更丰富多变 |
| 风格 / 画幅 / 分辨率 | 见第 2 步 |
| 视频模型 | 单次运行的覆盖选择，留空=用「设置」页里保存的默认值 |
| 配音 | Edge TTS（免费神经音）/ ElevenLabs / Formant（离线） |
| Draft | 半分辨率快速预览，成片时关掉 |

> **产品特性为什么重要**：这是 AI 认出品类的唯一依据。填「助眠灯」和填
> 「53度酱香型白酒」，模型写出来的会是完全不同的两套剧本——不填的话，
> 一瓶茅台和一只助眠灯会共用同一个模板文案。填好的特性还会作为
> 「镜头主体」写进每个分镜的画面提示词，保证产品前后一致。

点「生成 4 套广告脚本」→ 出现四张可编辑的脚本卡；点「下一步：分镜」进入第 2 步。
若 LLM 不可用，页面会**明确提示**已退回模板文案，而不是假装成功。

### 第 2 步：分镜确认

每一场都可以：改口播/字幕文案、改画面提示词、上下移动、删除，
也能「重新分镜」让模型再跑一次。字幕没有独立输入框——它靠这一行的词级
时间轴驱动，两者是同一份文本，改一个另一个跟着变。

镜头与视角用下拉选择（13 种镜头 × 11 种视角，中英文界面显示各自语言），
这些参数和风格、分辨率、视频模型一起拼进最终的画面提示词。

| 控件 | 说明 |
|---|---|
| 视觉风格 | `dr_vsl` / `comic` / `vector` / `claymation` / `talking_head` / `cinematic` |
| 画幅 | 9:16 竖屏、1:1、4:5、16:9 |
| 分辨率 | 540p / 720p / 1080p / 1440p / 4k。越高越贵，默认 1080p |
| 字幕 | 烧录字幕开关。关掉只留配音（字幕依赖配音波形，关字幕不关配音） |
| 视频模型 / 配音 | 单次运行的覆盖选择 |

> 场景数不是随意的：目标时长 ÷ 每场约 4 秒就是上限。文案太长时**合并**
> 场景而不是截断——被截掉的句子永远不会出现在成片里。

### 预览与统计

成片直接内嵌播放。下方三格统计：**时长 / 成本 / 场景数**。日志标签页里有更细的
`渲染 N 复用 M` —— 复用数就是「改一行不重渲全片」的直接证据。

### 微调（第 4 步）

用自然语言描述改动，例如：

- `开头再炸一点`
- `中段换成漫画风`
- `音乐换暗黑一点`
- `throughout the video, make it feel more premium`

后端返回解析结果：意图类型、受影响场景数、将要打的 patch 列表、以及模型给的理由。

> **当前状态**：改片端点只做**分析**（plan），还没有把 patch 应用后触发重渲染。
> 接上重渲染只需在 `/api/edit` 里调用 `apply_plan()` 再跑一次 `pipe.run()`。
> 保留分析态是为了让你先看清楚它会改什么，再决定要不要花钱重渲。

### 导出视频（第 5 步）

视频渲染完成后，第 5 步是「导出下载」：

- 在成片预览卡片或历史记录里点「下载视频（MP4）」，即可拿到 9:16 的 H.264 MP4。
- 拿到文件后，**自行上传**到任意短视频平台：TikTok / 抖音 / 视频号 / Instagram Reels / YouTube Shorts，按各平台常规流程发布即可。

> **为什么不做自动上传**：TikTok 的 Content Posting API 需要先过 2–6 周的
> Content Posting Audit，且未过审前所有发布强制 `SELF_ONLY`（仅自己可见）；
> 同时自动上传意味着要把账号授权交给本应用，对隐私敏感的用户不合适。
> 因此默认只提供下载，由用户自己上传。

### 历史记录与断点续渲

「历史」标签页列出所有跑过的成片与脚本批次，数据存在本地 SQLite
（`web/history_db.py`，WAL 模式），重启不丢。

**成片记录**每条带状态、场景数、耗时、成本，可以：

- 点开看只读摘要（每个场景的口播、提示词、状态）
- 下载成片 MP4
- **失败/部分完成时点「续渲」**——这是省钱的关键

**断点续渲**的原理：每个场景的内容寻址哈希没变，缓存里就还有那一段。
续渲只重跑真正失败或降级的场景，好场景直接从缓存取：

- `partial`（部分场景降级/跳过）→ **只**重跑那几场
- `failed`（整体报错）→ 重跑整片，但崩之前已经渲完的场景仍走缓存

所以「余额不足中断 → 充值后续渲」只付跳过那几段的钱，不用整片重来。

**脚本记录**列出每一批生成的 4 套方案，点一下可以把某一套标记为「已选用」，
并读回它的完整文案与产品特性——回到上一步时不会丢上下文。

## 架构说明

**为什么历史要落 SQLite**：早期成片记录只存在内存字典里，重启即失，
而且没法在多标签页之间共享。`web/history_db.py` 用 SQLite（WAL 模式，
`threading.Lock` 串行化写入）存两张表：`renders` 与 `scripts`。旧的
`renders.json` 会在启动时由 `migrate_json()` 一次性迁过去。
记录里存的是 **Project 的 JSON 快照**，不是 pickle——换版本也能读。

**为什么 Project IR 放内存**：`/api/edit` 需要拿到上一步的 IR 才能定位场景。
同进程内直接把 Project 对象存在 `_projects[job_id]` 里（热路径，避免反复
反序列化）是最简单的做法。**但跨重启续渲不能只靠它**——所以每次记录渲染
时，`_record_render` 会把它 `to_json()` 成 `project_json` 一并存进
`renders` 表。`_run_resume` 在内存里找不到 Project 时（服务器重启后必然如此），
就用 `Project.from_json()` 从 `project_json` 重建完整的 IR，再只重渲失败的
场景。这样「余额不足中断 → 重启 → 充值 → 续渲」才是一个真实的跨重启工作流，
而不仅仅是在同一进程生命周期内生效。

**续渲为什么能省钱**：场景是内容寻址的——同一份 IR + 同一份配置渲染出
同一个 hash，缓存里就还有那一段 mp4。续渲时用 `only={失败的场景 id}`
调 `pipe.run()`，好场景命中缓存直接复用，只有失败的场景真正调用厂商 API。
换分辨率会改变 hash——segment 缓存键里含 `w/h/fps`，所以缓存自然失效，这是预期行为。换厂商 key / 模型则属于视频生成层的另一条缓存路径，其失效策略由对应视频适配器的 cache key 决定。

**跨线程进度推送**：管线跑在 `run_in_executor` 的 worker 线程里，而
WebSocket 客户端在主 asyncio 循环上。所以启动时捕获主循环，worker 用
`asyncio.run_coroutine_threadsafe()` 调度广播。
直接在 worker 里调 `asyncio.get_event_loop()` 会抛
`There is no current event loop in thread` —— 这是踩过的坑。

**为什么密钥不进 `avb.toml`**：toml 是会提交进 git 的配置文件，
里面只写"用哪个 env var 存 key"。密钥统一落到 `.env`（已 gitignore），
写入时按行替换，保留文件里原有的注释与分组。

**并发**：一次一个任务最稳。多个任务同时跑会争 ffmpeg 和缓存目录；
真要并发需要给每个 job 独立的 workdir。
